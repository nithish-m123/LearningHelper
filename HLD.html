AI Exam Prep Focal Engine

High Level Design (HLD) · Version 3.0 · July 2026 · Final Year Project

1. Purpose & Scope

A web application that lets any college student upload their course materials (PDFs, PPTs) and immediately generates:

  • Structured topic explanations with math (KaTeX) and flowchart (Mermaid.js) visualizations
  • RAG-grounded answers scoped strictly to the uploaded material
  • Dynamic search mapping to the internet (Tavily AI) if course slides are empty or incomplete
  • Timed MCQ mock exams with score analysis and weak-area detection
  • Dedicated user guide page (/guide) explaining onboarding workflow steps

Constraints: Zero authentication, zero cost, zero local CPU/GPU usage for AI operations, temporary sessions self-destruct after 24 hours.

2. Design Patterns Applied

PatternWhere AppliedWhy
Repository Pattern lib/supabase.ts All data access goes through one typed interface. Swap database without touching routes.
Facade Pattern lib/session.ts Single entry point for all session operations (create, read, delete). Routes never touch cookies directly.
Strategy Pattern components/MarkdownRenderer.tsx Auto-detects whether to render Mermaid, KaTeX, dynamic SVG charts, or plain markdown based on AI output content type.
Stream Pipeline Native Fetch/SSE Browser and API routes communicate via native readable streams for zero-latency streaming text without third-party abstraction. Replaces AI SDK bound streams.
Singleton Pattern lib/gemini.ts (embedder) Transformer.js pipeline loads the model once; all calls reuse the same instance.
Factory Pattern lib/logger.ts (Thin formatter) Unified log factory outputs structured `[TIMESTAMP] LEVEL: Message` strings.

4. Anonymous Session Architecture

How It Works

No login. No passwords. Just a UUID cookie that identifies "this browser tab session."

1. User opens app
   → Browser checks cookie: "exam-session-id"
   → If missing: generate uuid(), store in cookie (24h expiry)
   → POST /api/session to log the new visitor in visitor_analytics

2. User uploads PDF
   → Upload request includes sessionId in header (X-Session-Id)
   → All document_chunks rows tagged: { session_id: "uuid-here" }

3. User searches a topic
   → /api/explain receives sessionId
   → Supabase query: WHERE session_id = $sessionId  ← isolation!
   → No other session can read your chunks

4. Session expires (24h)
   → Supabase cron (pg_cron): DELETE chunks WHERE created_at < NOW() - INTERVAL '24h'
   → User's cookie also expires in browser automatically

5. User clicks "Delete Session"
   → POST /api/session/delete with sessionId
   → Immediate DELETE on Supabase for that session_id

Data Isolation Guarantee

Every Supabase query on document_chunks is scoped with WHERE session_id = ?. User A's sessionId cannot access User B's chunks — the WHERE clause makes it structurally impossible.
